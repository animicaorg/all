# Bech32 Address Encoding Fix

## Problem Summary

The wallet and explorer were showing **incorrect balances** and **different addresses** than those in JSON files because there was a **mismatch in the bech32 address encoding** between Python and TypeScript implementations:

- **Python** (node, RPC server): Used **2-byte algorithm ID** in bech32 payload → 34 bytes total (alg_id + digest)
- **TypeScript** (SDK, wallet, explorer): Used **1-byte algorithm ID** in bech32 payload → 33 bytes total (alg_id + digest)

This caused addresses generated by one implementation to be **incompatible** with the other, leading to:
- Balance lookups failing or returning incorrect values
- Addresses displayed in the explorer not matching those in configuration files
- Cross-language operations (Python→TypeScript, TypeScript→Python) breaking

## Root Cause

### Python Implementation (Correct)
```python
# pq/py/address.py
payload = alg_id.to_bytes(2, "big") + sha3_256(pubkey)  # 2 + 32 = 34 bytes
```

### TypeScript Implementation (Incorrect)
```typescript
// sdk/typescript/src/address.ts (before fix)
const payload = new Uint8Array(1 + pkHash.length)
payload[0] = algByte  // 1-byte alg_id (WRONG!)
```

### Algorithm ID Mismatch
- **Python Registry** (`pq/alg_ids.yaml`): `dilithium3 = 0x1001`, `sphincs_shake_128s = 0x1002`
- **TypeScript** (before fix): `dilithium3 = 0x01`, `sphincs_shake_128s = 0x02`

## Fix Applied

### 1. TypeScript SDK (`sdk/typescript/src/address.ts`)
- Changed algorithm ID from 1 byte to **2 bytes big-endian**
- Updated `ALG_ID` constants to match Python registry: `0x1001`, `0x1002`
- Updated payload length check from 33 to **34 bytes**
- Fixed encoding/decoding to use 2-byte alg_id

### 2. Wallet Extension (`wallet-extension/src/background/keyring/addresses.ts`)
- Changed algorithm ID from 1 byte to **2 bytes big-endian**
- Updated `ALGO_IDS` constants to match Python registry: `0x1001`, `0x1002`
- Updated payload length check from 33 to **34 bytes**
- Fixed encoding/decoding to use 2-byte alg_id

### 3. RPC Layer (`rpc/methods/state.py`)
- Updated `DEFAULT_ALG_ID` from `1` to `0x1001` for address reconstruction
- Fixed all `AddressRecord` instantiations to use canonical algorithm ID
- This ensures addresses displayed by RPC match SDK-generated addresses

### 4. Tests
- Fixed `tests/integration/test_address_encoding.py` to expect 32 bytes (digest only) from `address_to_bytes()`
- Fixed hex address normalization tests
- Added cross-language compatibility test

## Verification

### Python Address Generation
```python
from pq.py.address import address_from_pubkey, decode_address

pubkey = b'\x01' * 48
alg_id = 0x1001  # dilithium3

addr = address_from_pubkey(pubkey, alg_id)
# Result: anim1zqqhej6vejt4rren3q9rxs7gqw56ecfs4fw64sfh939vxv9x4xc7x0slx80pd

rec = decode_address(addr)
# alg_id: 0x1001 ✓
# digest: 32 bytes ✓
```

### TypeScript Compatibility
After the fix, TypeScript can now correctly decode Python-generated addresses:
```typescript
import { decodeAddress } from './sdk/typescript/src/address';

const addr = "anim1zqqhej6vejt4rren3q9rxs7gqw56ecfs4fw64sfh939vxv9x4xc7x0slx80pd";
const decoded = decodeAddress(addr);
// algId: 0x1001 ✓
// pubkeyHash: 32 bytes ✓
```

## Breaking Changes

**Important**: This fix changes the address format for TypeScript-generated addresses. 

### Migration Path
1. **New addresses**: All new addresses will use the correct 2-byte algorithm ID format
2. **Old addresses**: Addresses generated with the old 1-byte format will need to be regenerated
3. **State DB**: The state database stores accounts by 32-byte digest only, so the underlying account keys remain unchanged

### Compatibility
- **Forward compatible**: Old addresses in state DB continue to work (digest is the key)
- **Address display**: Old addresses displayed using 1-byte alg_id will now show with 2-byte alg_id (visual change only)
- **JSON configs**: May need to regenerate addresses in configuration files if they were created with TypeScript
